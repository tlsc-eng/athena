# Performance baseline, v0.2 → e-perf (October 2026)

Phase E of the v0.3 roadmap: measure first (E0), then E1 (terminal row cache), E4 (foreground
poll off the daemon lock), E5 (non-blocking delivery, lagging clients dropped), E6 (closed tabs
leaked a `mux-read` thread). E2 (shell re-render fan-out) and E3 (notices cap) are measured here
but implemented by other lanes.

## Method

- Release builds of `athena` and `athena-mux` from the same tree before and after the changes
  (`cargo build --release -p athena -p athena-mux`). Both carry the same instrumentation: one
  `trace!(target: "athena::render", us, ...)` per `TerminalElement::prepaint`.
- Isolated `HOME`, a seeded workspace with one project and ten terminals in a 2 × 5 split, all
  visible (only visible tabs get a view and a daemon connection).
- 5 minutes idle, then 5 minutes with the top-left terminal running
  `while true; do date; ls -la /usr/bin | head -40; sleep 0.05; done` (about 40 KB/s).
- Every 10 s: `ps -o rss=,%cpu=,time=` and `ps -M` thread count for the app and the daemon.
  CPU is Δcputime / Δwall over the phase, not the decaying `%cpu` column.
- `footprint` at start and end, `sample <pid> 10` halfway through the output phase, thread names
  from `sample <pid> 1`.
- macOS `ps -M` has no thread names, so `ps -M | grep -c mux-read` always prints 0; the
  `mux-read` counts below come from `sample <pid> 1 | grep -c ': mux-read'`.
- Thread and socket counts include the notices subscriber, which holds one connection and one
  `mux-read` thread of its own: ten terminals means 11.

The screen of the test machine was locked for every run (the user was away), so the window drew
no frames: see "Rendering" for what that leaves unmeasured.

## Results: resources (10 terminals, screen locked)

| Metric | before (v0.2.0) | after (e-perf) |
|---|---|---|
| App CPU, idle 5 min | 0.00 % | 0.00 % |
| App CPU, printing 5 min | 0.34 % | 0.36 % |
| Daemon CPU, idle 5 min | 0.08 % | 0.07 % |
| Daemon CPU, printing 5 min | 0.16 % | 0.17 % |
| App RSS start → end of idle | 89.9 → 86.8 MB | 89.6 → 70.0 MB |
| App RSS end of printing (max) | 78.1 MB (94.8) | 77.7 MB (77.7) |
| App phys_footprint start / end | 60 / 61 MB | 49 / 51 MB |
| Daemon RSS start → end (printing) | 4.4 → 11.1 MB | 4.5 → 14.3 MB |
| Daemon phys_footprint start / end | 3.5 / 13 MB | 3.6 / 13 MB |
| App threads (`ps -M`) | 18 → 18 | 19 → 19 |
| App `mux-read` threads | 11 | 11 |
| Daemon threads | 45 → 45 | 45 → 45 |

The daemon's growth while printing is the pane's scrollback ring filling towards its 8 MB cap.
Without frames the app only parses output, so its CPU is the same before and after; the
footprint difference at start is allocation noise from launch, not something these changes did.
`sample` during output shows every app and daemon thread parked in `recvfrom`, `read`,
`semaphore_wait_trap` or `workq_kernreturn` in both builds: nothing is hot without rendering.

## Results: rendering

Not measured. With the screen locked the window gets no display-link ticks: the trace counter
logged 20 prepaints (two frames for ten panes) at launch and none afterwards, even with the
printer running, in both a hidden and a shown window. The before and after binaries are kept in
the lane scratchpad so this can be repeated on an unlocked machine:

```
HOME=/tmp/athena-qa-e-perf ATHENA_LOG=info,athena::render=trace <bin>/athena
grep -c 'terminal prepaint' app.log          # prepaints per second, per pane
grep -o 'us=[0-9]*' app.log | sort -t= -k2 -n # prepaint time
grep -o 'rebuilt=[0-9]*' app.log              # rows rebuilt (after only)
```

Expected from the code: any pane's output redraws the whole window, so every visible terminal
prepaints at the printer's frame rate. Before, each of those walked every cell and shaped every
run; after, an idle pane rebuilds no rows (only the cursor row when the cursor moves) and reuses
its cached quads and shaped lines. The invalidation rules are covered by unit tests in
`athena-term/src/element.rs` and `terminal.rs`.

## Results: lifetimes and lagging clients

| Check | before | after |
|---|---|---|
| Closed tab's `mux-read` thread | stays blocked forever (the reader holds a dup'd fd, dropping `Connection` never EOFs it) | exits: `TerminalView` closes the connection on drop and before every reconnect |
| `mux-read` after opening and closing 20 terminals | not measured (needs Cmd+T / Cmd+W, which a locked screen does not deliver) | not measured; covered by a unit test that `Connection::close` ends a reader blocked on the cloned stream |
| A client that stops reading, other client on the same pane | stalls (daemon test: 3 ticks, then still 3) | keeps flowing; stalled client is hung up after 2 s of a full queue |
| Foreground updates while one client is stalled | stop for every pane (poller blocked in `send`) | continue |
| GUI stopped with `SIGSTOP` for 30 s while printing | n/a | daemon logs `client 2 stopped reading; disconnecting it`; after `SIGCONT` the app logs `session daemon dropped a lagging terminal; reattaching`, no "Lost the connection", the terminal shows live output again, `mux-read` stays at 11 |

## Not done here (other lanes)

- **E2** (coalescing `TerminalEvent::Changed` into one Shell redraw per 16 ms, `sync_previews`
  early return, Playwright config lookup once per palette open) landed in the `c-ux` lane.
- **E3** (the `KEEP` trim for local notices) landed in the `b-items` lane.
