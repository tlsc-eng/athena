# Performance re-baseline, v0.9.0 (October 2026)

v0.10's QA lane repeated the E0 protocol of [the v0.2 baseline](2026-10-v0.2.md) on the installed
v0.9.0, added the editor, language server and git load the v0.10 plan asks for, and compared the
results. The rule was to fix anything more than 20 % worse than before; nothing in CPU time,
dirty memory, file descriptors or the editor benchmarks was, so no performance change was made.

## Method

- Binaries: a copy of `/Applications/Athena.app` 0.9.0 (release, 47 MB `athena`), and as a
  control the v0.2 e-perf build kept from that lane (22 MB `athena`), run the same day on the same
  machine under the same conditions. The v0.2 document's own numbers were taken with the screen
  locked; these were taken with it unlocked and with other work running (load average 6 to 8), so
  the control run, not the old table, is the comparison that counts.
- E0, unchanged: isolated `HOME`, one empty (non-git) project with ten terminals in a 2 × 5
  split, hidden window, 5 minutes idle, then 5 minutes with the top-left terminal running
  `while true; do date; ls -la /usr/bin | head -40; sleep 0.05; done`. Every 10 s: RSS, CPU time
  and threads (`ps`, `ps -M`) and now open files (`lsof -p | wc -l`) for the app and the daemon.
  CPU is Δcputime / Δwall, which the machine's other load does not change much.
- Extended (v0.10 plan): a local clone of the athena repository as the project (330 tracked
  files, git), ten terminals, one printing Claude Code-like output (a `\r` spinner line, coloured
  tool headers and diff lines, about 20 lines a second), and two Go editors of 2 000 and 10 000
  lines open beside them with gopls 0.23, inlay hints on and the minimap and semantic tokens at
  their defaults; 30 minutes, sampled as above.
- Editor work per keystroke and per paint: the ignored benchmarks kept in the tree, five runs,
  best average reported (the machine was busy):
  `cargo test -p athena-editor --release --lib -- --ignored keystroke_cost semantic_cost paint_cost --nocapture`
- Git: the MCP `git_status` tool's round trip against the extended project's clone, and
  `git status --porcelain=v2 -b` on its own for reference.

## Results: E0 (ten terminals)

| Metric | v0.2 table (locked) | v0.2 control (today) | v0.9.0 |
|---|---|---|---|
| App CPU, idle 5 min | 0.00 % | 0.01 % | 0.01 % |
| App CPU, printing 5 min | 0.36 % | 0.31 % | 0.30 % |
| Daemon CPU, idle 5 min | 0.07 % | 0.05 % | 0.06 % |
| Daemon CPU, printing 5 min | 0.17 % | 0.20 % | 0.20 % |
| App RSS start → end of idle | 89.6 → 70.0 MB | 89.8 → 70.5 MB | 101.3 → 89.4 MB |
| App RSS end of printing (max) | 77.7 MB (77.7) | 73.1 MB (80.1) | 78.0 MB (97.3) |
| App phys_footprint start / end | 49 / 51 MB | 60 / 61 MB | 65 / 65 MB |
| Daemon phys_footprint start / end | 3.6 / 13 MB | 3.5 / 13 MB | 3.5 / 13 MB |
| App threads (`ps -M`) | 19 → 19 | 19 → 18 | 26 → 24 |
| App `mux-read` threads | 11 | 11 | 11 |
| App / daemon open files | — | 58 / 74 | 58 / 75 |
| Daemon threads | 45 → 45 | 45 → 45 | 45 → 45 |

- CPU is the same within noise in both phases, for the app and the daemon.
- Dirty memory (phys_footprint) is 4 to 5 MB, about 8 %, above the control: `Malloc Small` 24
  against 22 MB and a little more `__DATA` and graphics. The 11 MB gap to the v0.2 table is
  `IOSurface` (16 MB locked, 25 MB unlocked in both builds), so it comes from the screen state,
  not the code.
- RSS is about 19 MB (27 %) higher at the end of the idle phase. It counts clean, file-backed
  pages, and v0.9's binary is twice v0.2's (47 against 22 MB; `__TEXT` resident 4.3 MB against
  1 MB) with more grammars and mapped files (12 against 10 MB); the dirty share moved by the 8 %
  above. Not treated as a regression.
- Six more threads: three `notify-rs fsevents loop` threads and three `athena-watch` debounce
  threads, one pair each for the project folder (the file tree's live updates, v0.3), settings.json
  and keymap.json (live reload, v0.5 and v0.6). All are parked when nothing changes. The settings
  and keymap watchers watch the same data folder; sharing one would save two threads, but
  x10-ui is reworking both files' editors this release, so it is left as a follow-up.

## Results: editor benchmarks

| Case | earlier baseline | v0.9.0 tree, best of 5 |
|---|---|---|
| 2 k-line Rust file, UI thread per key (background parse) | 0.15 ms avg, 0.24 ms p99 (v0.5) | 0.18 ms avg, 0.36 ms p99 |
| 2 k-line Go file, keystroke + 60-line highlights, semantic layer on | 0.193 ms (v0.9) | 0.223 ms |
| 10 k-line Go file, same | 0.446–0.454 ms (v0.9) | 0.519 ms |
| Decode and place all tokens, 2 k / 10 k lines | 0.44–1.12 / 2.1–2.3 ms (v0.9) | 0.44 / 2.44 ms |
| Markdown, 60 lines of a 20 k-line paragraph | 2.1 ms (v0.7) | 2.26 ms |
| JSON 300 k array, open brackets, first call / scrolling | 13.4–16.5 / 0.002 ms (v0.7) | 14.9 / 0.002 ms |

All within 20 %, and with and without the semantic layer still within noise of each other. The
worst, 14–19 %, are the per-key averages, measured at a load average of 7 while other lanes
compiled; the earlier baselines were taken on an otherwise idle machine. Every case stays far
inside the 16 ms keystroke-to-paint budget.

## Results: extended load (30 minutes)

| Metric | start | after 30 min |
|---|---|---|
| App CPU over the 30 minutes | — | 0.17 % (3.1 s) |
| Daemon CPU | — | 0.16 % (2.9 s) |
| gopls CPU and RSS | — | 0.64 % (11.5 s), 183 MB |
| App phys_footprint | 83 MB | 84 MB |
| App RSS (max) | 94 MB | 60 MB (97) |
| App threads / open files | 27 / 63 | 26 / 63 |
| Daemon threads / open files | 45 / 74 | 45 / 74 |
| Daemon phys_footprint | 3.6 MB | 8 MB |

- Memory is flat after the first five minutes (RSS between 56 and 60 MB from minute 6 to 30,
  footprint within 1 MB); thread and file counts do not move. Nothing grows with time.
- The two editors and gopls add about 19 MB of dirty memory to the E0 figure (footprint 84
  against 65 MB, nearly all `Malloc Small`), three threads (`lsp-gopls`, `lsp-reader`, `lsp-writer`) and five files.
- `git_status` through MCP answers in 59 ms on a clone of the same repository (`git status --porcelain=v2 -b` alone:
  10 ms warm, 70 ms cold); the app runs it off the UI thread.
- There is no earlier number for this load; this is the baseline for v0.11.

## Rendering

Not measured, as in v0.2: the hidden QA window drew two frames at launch (20 terminal prepaints)
and none afterwards, so per-frame paint cost, and anything requested per frame (semantic tokens,
inlay hints and code lenses are asked for as the editor paints), did not run in the hidden
window. The same holds for the extended run, so its CPU figures cover output parsing, gopls traffic and
git, not drawing. Rendering with a shown window needs the machine to be idle and unlocked for the
whole run, which it was not while this lane ran.
