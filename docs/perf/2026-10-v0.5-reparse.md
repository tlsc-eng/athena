# Keystroke cost, tree-sitter reparse off the UI thread (October 2026)

v0.5 follow-up: a keystroke in a 2 k-line Rust file cost about 7 ms on the UI thread, nearly all of
it the incremental tree-sitter reparse. Editor tabs now move the old tree past each edit at once
(`Tree::edit`, so highlights shift with the text) and reparse on the background executor; the new
tree is swapped in when it lands and the tabs on that file redraw.

## Method

Same as the x5-edit lane's measurement, now kept in the tree as an ignored test:

```
cargo test -p athena-editor --release --lib -- --ignored keystroke_cost --nocapture
```

- A generated Rust file of 400 five-line functions (2 001 lines).
- The caret at line 1 000, column 4; `let value = compute(a, b);\n` typed 40 times through
  `Buffer::type_char` / `Buffer::newline` (1 080 keystrokes, auto-closing pairs included).
- One sample per keystroke: the edit plus highlighting the 60 lines around the caret, which is
  what the UI thread does before it can paint.
- Three modes: `sync` (the old path: parse inside the edit); `background` with each parse run to
  completion between keys (typing slower than a parse, the common case), timed separately; and
  `background` with parses never landing before the next key (typing faster than parses).
- Apple M5, rustc 1.98.0, release profile. Two runs; they agreed within 2 %.

## Results

| Mode | avg | p50 | p99 | max |
|---|---|---|---|---|
| sync, UI thread per key (before) | 7.2 ms | 9.7 ms | 11.6 ms | 12.0 ms |
| background, UI thread per key (after) | 0.15 ms | 0.16 ms | 0.24 ms | 0.28 ms |
| background, the parse itself (off the UI thread) | 7.0 ms | 9.5 ms | 11.3 ms | 11.8 ms |
| background, typing faster than parses, UI thread per key | 0.52 ms | 0.17 ms | 10.0 ms | 12.0 ms |

The UI thread's share of a keystroke drops about 48×, well inside the 16 ms keystroke-to-paint
budget. The parse costs the same as before; it now runs beside the UI, and the frame with its
highlights follows the keystroke's frame by about one parse.

The last row's tail is the keys that open a pair (`(`, `"`, …). Whether to auto-close depends on
whether the caret is in a string or comment, which needs the last keystroke's tokens, so such a key
parses inline when a background parse has not landed yet. Other keys never wait.

The benchmark types into a function name, which leaves syntax errors across the rest of the file;
that is why the incremental parse costs a full 7 to 10 ms here. It is kept as is so the numbers
compare with x5-edit's.

## What reads the tree while a parse is pending

- Highlights: the edited old tree, so existing tokens move with the text and new text takes its
  surroundings' colour until the parse lands.
- Bracket match and folds: the edited old tree, with each pair checked against the text; a pair
  the text no longer holds falls back to the plain nesting scan. Each view's fold cache is cleared
  when a parse lands.
- Auto-closing pairs: parse inline first, as above.
- A parse in flight when the tree is parsed inline, or when the file changes language, is dropped
  when it lands. Edits made while a parse runs are replayed on its tree, and another parse follows.
