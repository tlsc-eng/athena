# Paint cost of huge Markdown paragraphs and JSON arrays (October 2026)

v0.7 review items M9 and M10: two per-paint costs grew with the size of a single syntax node, not
with what is on screen.

- M9: Markdown inline highlighting (emphasis, code spans, links) re-parsed the whole paragraph's
  `inline` node with the inline grammar on every paint. A paragraph of 20 k lines cost about a
  third of a second per frame.
- M10: bracket pair colouring asks the tree for the brackets open at the first visible line, which
  walked every child before that byte of each enclosing node, every frame. Inside a JSON array of
  300 k elements that is 300 k siblings per frame.

## Method

Kept in the tree as an ignored test:

```
cargo test -p athena-editor --release --lib -- --ignored paint_cost --nocapture
```

- Markdown: one paragraph of 20 000 lines, each with emphasis, strong text and a code span,
  highlighting the 60 lines from line 10 000, as a frame does. 20 calls.
- JSON: a 300 000-element array, one element per line. `open_brackets_at` at the start of line
  150 000 (the first call after a parse), then 60 calls a line further each, as scrolling does.
- Apple M5, rustc 1.98.0, release profile. At least two runs each; Markdown runs agreed within 3 %,
  the first JSON call varied between 13 and 17 ms.

## Results

| Case | before | after |
|---|---|---|
| Markdown, 60 lines of a 20 k-line paragraph, per paint | 318 ms avg, 329 ms max | 2.1 ms avg, 4.1 ms max |
| JSON 300 k array, open brackets, first call after a parse | 13.5 ms | 13.4–16.5 ms |
| JSON 300 k array, open brackets, each later frame (scrolling) | 13.5 ms avg | 0.002 ms avg, 0.009 ms max |

The reviewer measured 354 ms and 40 ms per call in a debug build; the ratios are the same.

## What changed

- The inline grammar now parses only the painted lines and 20 lines either side
  (`INLINE_CONTEXT_LINES`), and the walk over the `inline` node's children for quote and list
  continuations starts at that window rather than at the paragraph's first line (a long paragraph
  has one child per line; walking them was 13 ms of the remaining cost). Emphasis or a code span
  that opens more than 20 lines above the view and closes inside it is painted as plain text.
  Paragraphs that fit in the window are parsed exactly as before.
- Each node with 64 or more children keeps what has been read of its bracket tokens, by node id,
  until the tree changes (`Syntax::brackets`, cleared on every edit, reparse and landed background
  parse). A later call reads only the children past the furthest byte read so far, so scrolling
  down a huge array costs nothing and scrolling up reads nothing. Nodes with fewer children are
  read directly, as before.

## Still open

- The first frame after each tree change inside a huge array still reads every element above the
  view once (about 13 ms at the middle of 300 k elements). A keystroke changes the tree twice
  (the edit, then the background parse landing), so typing deep in such a file pays it twice.
  Making it independent of position would need an index of bracket tokens maintained across
  incremental parses.
- Sticky scroll headers use the fold cache, not these bracket scans, so nothing was shared there.
